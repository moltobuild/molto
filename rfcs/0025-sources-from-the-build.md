# RFC 0025: Sources From the Build

- RFC Number: 0025
- Title: Sources From the Build
- Status: Draft
- Created: 2026-10-07

## Summary

A delegated recipe (RFC-0009, `via = "delegate"`) may let upstream's own build
say what to compile. After configuring, molto asks it — `make -n` for a
Makefile, `compile_commands.json` for CMake — and takes every compile line it
would have run: the file and the arguments upstream gives it. molto still
compiles each of them itself, with its compiler, its cache and its link.

Three things come with it, because the first library that needs this is
FFmpeg and FFmpeg needs all three:

- **Assembly.** A `.S` file is compiled by the C compiler; a `.asm` file by
  NASM, which molto finds the way it finds CMake (RFC-0023).
- **Placeholders in `[build].args`.** `{cc}` and `{nasm}` are replaced by what
  molto resolved, for a configure that takes its tools as arguments instead of
  from the environment.
- **A configuration that sees its dependencies built.** A delegated package's
  source dependencies are compiled and archived before its configure runs, so
  a probe that links against them finds them.

## Motivation

`[artifacts].sources` names files one by one, and that was right for libpq
(38 files) and libwebsockets (around 100). FFmpeg compiles 2073 files on
arm64 with everything it offers turned on, more on x86-64, and which ones
depends on what its `configure` found. A list that size copied into the recipe
is derived from upstream, has to be regenerated by hand for every release and
every platform, and is wrong the moment one of them differs. Upstream's build
already knows the answer on every machine; asking it is the same move RFC-0009
made for `config.h`.

The per-file arguments matter as much as the files. FFmpeg compiles each
library with `-DBUILDING_avcodec` (or `_avformat`, …), its `.S` files without
`-std`, and its `.asm` files with a NASM command line of its own. One set of
flags per package, which is what a recipe can say today, cannot describe that.

Molto's promise is that a programmer writes code and gets every dependency
complete and fast. For FFmpeg, complete is every codec and format it builds
without external libraries; fast is its hand-written SIMD (NEON in `.S` on ARM,
NASM on x86) and its hardware decoders. Both are out of reach without this.

## Design

### `[build].sources`

```toml
[build]
system = "autotools"
via = "delegate"
args = ["--cc={cc}", "--x86asmexe={nasm}", "--disable-programs", "--disable-doc"]
targets = ["libavutil/ffversion.h"]
sources = "make"
goals = ["libavutil/libavutil.a", "libavcodec/libavcodec.a"]

[artifacts]
type = "source"
```

- **`sources = "make"`**: after configuring, molto runs `make -n -B <goals>`
  in the source and reads the compile lines it prints. `-n` runs nothing; `-B`
  prints every line whatever the tree's state. `goals` is optional and defaults
  to make's own default goal.
- **`sources = "cmake"`**: molto reads `.molto-cmake/compile_commands.json`,
  which the configuration then writes (`-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`).
  `goals` is refused.
- **`[artifacts].sources` must then be absent.** Both is an error, not a
  merge. `[artifacts].exclude` still applies, to the paths as they were read.
- **A compile line** is a line whose first word is the compiler molto passed
  (`{cc}`, or `CC` for a configure that reads it) or the NASM it resolved, that
  compiles one file inside the source to an object. Anything else make prints —
  `ar`, `ranlib`, scripts writing version files — is ignored: molto archives
  and links on its own.
- **What molto keeps of a line**: the source, and every argument but the
  driver, the input, `-c`, `-o <file>` and the dependency-file flags (`-MMD`,
  `-MD`, `-MF`, `-MT`, `-MQ`, `-MP`), which are molto's to choose. A relative
  include (`-I.`, `-I./compat`, `-include`, NASM's `-P`) is made absolute
  against the source root. The words are split as `sh` splits them.
- **A source the build generates** is asked of make by its own rule before
  anything compiles it: FFmpeg 9 writes its NEON tables (`ops_neon.gen.S`)
  with a program it compiles first.
- **Kept with the configuration.** The list is written to `.molto-sources`
  beside the stamp (RFC-0009) and read back while the stamp holds; a new
  configuration reads it again.

### What reaches the compiler

A unit read from the build is compiled with upstream's arguments in unit
scope, after molto's (RFC-0013): the profile's `-O0 -g` and the toolchain's
floor first, then upstream's `-O3`, its defines and its warnings, which win.
`[artifacts].std` is not added; upstream's line already says it. A dependency
is therefore optimised the way upstream optimises it in every profile, which
is what anyone linking FFmpeg expects of it.

The interface of the package's own dependencies (their include directories and
defines) is added as for any recipe. Its own interface is not: it is for its
consumers, and FFmpeg's installed `molto/include/libavutil/common.h` ahead of
upstream's `-I.` would be found instead of the one whose neighbours it
includes.

Objective-C (`.m`, FFmpeg's AVFoundation and CoreImage code on macOS) goes to
the C driver too, which compiles it by its extension.

### Assembly

- **`.S` and `.s`** go to the C driver molto resolved, like a `.c`.
- **`.asm`** goes to NASM: `nasm <upstream's arguments> -MD <depfile> -o
  <object> <source>`. The depfile feeds the cache like a compiler's does.
- **NASM is found like CMake**: `$MOLTO_NASM`, then `pickup tools`, then
  `nasm` on the PATH. molto never installs it. A recipe that compiles `.asm`
  on a machine without NASM fails naming `pickup install nasm`.

Sources discovered in a drop (no `sources` at all) stay `.c`, `.cc` and `.cpp`:
assembly is compiled only when a build or a recipe names it.

### Frameworks

A `link` entry written `VideoToolbox.framework` is a macOS framework and
reaches the link line as `-Wl,-framework,VideoToolbox`, one word. Everything
else stays `-l<name>`.

### Placeholders

In `[build].args` and `[build].env` values, `{cc}` becomes the compiler molto
resolved and `{nasm}` the NASM it resolved, written as a shell reads them. On
a machine whose target is not x86, a missing NASM is not an error: `{nasm}`
becomes `nasm`, which a configure for another architecture never runs. What
they expand to is part of the stamp's digest.

### A configuration that sees its dependencies built

Today a delegated configure runs before any dependency compiles, so a probe
that links (`check_lib zlib zlib.h zlibVersion -lz`) fails and the recipe has
to turn the feature off. For FFmpeg that means no PNG.

Now a delegated package's source dependencies are compiled first, each
archived as `lib<name>.a` in a directory of the build, and that directory
reaches configure as an `-L` with the package's includes, as RFC-0009 already
does for platform packages. The rest of the build then proceeds as before; the
objects are the same ones, taken from the cache.

### Schema

`[build].sources` and `[build].goals` are schema 5. A reader that predates
them would find no `[artifacts].sources`, compile every file in the tarball,
and fail far from the cause, so it must refuse.

## Security

`via = "delegate"` already runs upstream's configure on the consumer's
machine; `make -n` runs nothing new beyond make reading its Makefiles. The
arguments taken from a compile line are upstream's, chosen by the same code
the recipe already trusts, and reach only that package's own units — never its
consumers. A line naming a file outside the source is refused.

## Alternatives

- **Raise the 128-file limit and list everything.** Two thousand lines per
  platform, derived from upstream and stored in the recipe: what RFC-0009 set
  out never to host.
- **Let make build the library.** Gives up molto's compiler choice, its object
  cache, its compile database and its control of the link — the reasons a
  dependency is compiled by molto at all.
- **Parse FFmpeg's Makefiles.** `OBJS-$(CONFIG_H264_DECODER) += …` is make, and
  only make evaluates it faithfully.

## Rollout

1. `[build].sources` (`make`, `cmake`), placeholders, schema 5.
2. Assembly and NASM.
3. Configuration after the dependencies are built.
4. Recipes: FFmpeg 8 complete, with SIMD and the platform's hardware decoders;
   then dav1d, for AV1.
